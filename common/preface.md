# 前言

本项目的重点不在软件业务逻辑本身，而是给大家提供一个接触工程开发的入口。业务需求只是学习载体，你真正要学习的是软件开发的工作流、开发习惯、验证方法和工程思维。

我们希望你以求知的心态做项目：完成功能只是学习过程的产物，理解每个部分的目的和行为才是重点。遇到不熟悉的工具、命令、库函数或框架行为时，先弄清它解决什么问题、为什么在这里，再把它用到自己的实现中，而不是盲目地复制粘贴 AI 的结果。

## 发现问题

发现问题不只是等到程序报错才开始。看到没有见过的工具、操作、文件或语法时，可以先停下来问一句：它在当前项目里承担什么职责？为什么这里需要它？如果删掉、改掉或换成另一种写法，可能影响什么？

例如 Python 路线会引导你运行 `uv sync --locked`。这时可以继续追问：`sync` 在做什么？`--locked` 是在避免什么问题？`.venv/`、`uv.lock` 和 `pyproject.toml` 分别是什么关系？`uv run ruff` 又是什么意思？`ruff` 从哪里来？看到项目里的空 `__init__.py`，也可以问它为什么存在、删除后会影响哪些导入。Rust 路线会遇到同类问题，例如 `Cargo.toml` 和 `Cargo.lock` 的关系、`cargo check --locked` 的含义、crate 和 module 如何组织。

进入实现后，业务现象会成为新的工程问题的入口：

- 上传文本后列表没有变化：请求真的成功了吗？数据是否写入？列表查询是否正确？令牌是否指向了另一个用户？
- 明明刚登录却收到 401：客户端是否携带令牌？令牌是否过期或被替换？服务端是否按预期识别身份？
- 两个请求同时注册同名用户：项目规范要求几次成功？共享状态是否会被破坏？
- 异步服务端处理密码计算时响应变慢：哪些操作占用了事件循环？阻塞工作应该放在哪里？

这类问题不必一次性追问到底。可以先弄清它在当前任务中的作用，判断它是否影响正确性、安全或后续设计；对暂时不展开的问题做好记录，之后在相关任务中继续学习。不要为了“彻底搞懂某个工具”无限扩展，而忘记项目本身要解决的问题。

## 学习方法

遇到不熟悉的内容时，优先查官方文档；其次是他人总结的博客、教程和讨论，把它们当作理解路径或补充材料，而不是权威结论。检索时尽量带上准确的命令、文件名、报错、库名和版本，避免把不同版本的行为混在一起。

读文档不需要从第一页读到最后一页。可以先定位到当前问题相关的章节，弄清输入、输出、适用范围和注意事项，再回到项目里验证。看完资料后，用自己的操作或测试确认行为；如果暂时不能解释，就把它还原成更小的问题继续查。

如果使用 AI，可以让它解释概念、对比方案或提示排查方向。AI 给出的代码和结论最好通过自己的操作验证，或回到官方文档求证。不要把“看起来能跑”当作已经理解。

## 学习的取舍

学习不可能一次学完，也不必追求把所有细节都背下来。可以根据内容在项目中的作用分层取舍。

- **需要理解并能说明取舍的工程问题**：HTTP 请求与响应的含义、身份验证、用户数据隔离、共享状态保护、异步阻塞和并发行为，以及测试与验证的目的。这些是通过当前业务载体暴露出来的通用工程问题，需要能解释它们的行为和影响。
- **知道即可**：常用命令、框架 API、配置项和参数形式。需要知道它们大概解决什么问题、在哪里查；具体写法可以随时检索官方文档，不必背诵。
- **忘记也没关系**：精确语法、函数签名、选项组合和样板写法。忘记后能快速找到资料，并通过运行或测试确认，就足够了。

判断学到什么程度，可以看自己是否理解当前问题、是否能解释为什么这样改、是否能预判影响范围并设计验证。达到这个程度就可以继续推进任务；工具和框架的内部细节，等真正需要时再深入。

这并不意味着可以忽略项目要求的功能；正确实现和验证协议规定的业务行为，仍然是完成项目的必要基础。学习重点不在于扩展业务深度，而在于通过这些行为理解工程问题。

## 面试方向

面试可能围绕你的学习过程、设计取舍、实现理解、验证方法和继续学习的意愿展开，不会检查你是否记住了某个命令、语法或业务领域知识。你可以说明自己完成了什么、还没有完成什么，以及为什么这样安排。
